# UI 与交互体验升级方案

日期：2026-09-16。审阅基线：6318276；线上运行代码：9a858c6。

状态：审阅与计划完成，以下实施批次尚未开始。本轮没有安装 UI 依赖或修改运行代码。

## 1. 结论

推荐 **按需引入 shadcn/ui（Radix 版本），统一暖纸主题，自行设计游戏专属组件与流程**。

如果按用户提出的两个方向划分，基础组件优先选择现成的；游戏交互由我们写。衡量效率应包含视觉反复调整、键盘 / 触摸边界、测试和长期维护，而不只是首次写出 JSX 的速度。

现有纸色、墨色、橙色与桌面画布 / 猜词双栏值得保留。最需要投入的是控件一致性、操作连续性、不同角色的界面，以及等待 / 成功 / 失败的反馈。成熟演示页面的完成度来自这些细节共同工作，不能由安装组件库保证。

### 方案比较

以下是结合当前 React 19 + Vite + JSX + 普通 CSS 的工程判断，尚未进行各方案的实际包体和耗时对照实验。

| 路线 | 首次接入 | 达到统一视觉的工作 | 游戏适配与维护 | 本项目判断 |
| --- | --- | --- | --- | --- |
| 全部自行实现 | 最少配置 | 按钮、弹窗、提示、选项、状态均需逐项设计 | 所有交互边界与样式都由项目维护 | 自定义自由，但总成本最高，不优先 |
| Radix / Base UI + 全部自写样式 | 能沿用当前 CSS | 行为有基础，外观仍需从头打磨 | 适合已有成熟设计规范的项目 | 可行的轻量备选，仍需补本项目最弱的视觉基础 |
| **shadcn/ui 按需引入 + 游戏组件定制** | 需引入 Tailwind，处理旧 CSS | 组件已有统一起点，集中调整主题与密度 | 基础源码归项目；交互底层使用成熟实现 | **推荐，质量与总投入最均衡** |
| Mantine 整套主题与组件 | Provider / CSS 接入清楚，基础页面快 | 标准表单很快；游戏画室仍需专门调样式 | 同样不能替代画布、回合、猜词设计 | 若目标是以表单为主会更有优势，本项目收益较小 |

shadcn 是可放进仓库修改的组件源码体系，不是装好即完成设计的皮肤。官方提供 Vite 与 JavaScript 方案，业务代码可继续 JSX。选择 Radix 版本是为了保持一套一致的组件来源和交互 API；Base UI 也可行，本轮没有证据表明它性能更差，不同时引入两套。[官方介绍](https://ui.shadcn.com/docs)、[Vite 接入](https://ui.shadcn.com/docs/installation/vite)、[JavaScript](https://ui.shadcn.com/docs/javascript)、[Radix 介绍](https://www.radix-ui.com/primitives/docs/overview/introduction)、[Base UI](https://base-ui.com/react/overview/quick-start)、[Mantine](https://mantine.dev/getting-started/)。

## 2. 当前体验的具体短板

区分已在浏览器复现的问题、源码直接可见的行为和仍待设备测试的风险。

| 优先级 | 发现与证据 | 对使用者的影响 | 目标行为 |
| --- | --- | --- | --- |
| P1 | 手机色块按钮宽 27px，滑杆宽 44px；工具条自由换行。源码及已保存手机截图 | 难精确点按，清空落单，工具关系不清楚 | 工具分组；粗指针触控目标至少 44×44px；颜色 / 笔宽按需展开 |
| P1 | App 的单个 busy 传给猜词、裁定及其他操作；猜词输入在请求期间 disabled。源码 | 高延迟下不能连续输入，焦点 / 软键盘连续性有风险 | 每类操作独立 pending；输入保持可编辑，防止重复提交同一条 |
| P1 | 顶部 error / notice 在正常文档流中。源码和上轮公网验收 | 一次反馈会使画布、控件整体位移 | 字段错误就地出现；复制等短反馈用浮动通知；网络状态占稳定位置 |
| P1 | 清空、结束本轮、进行中离房直接执行。源码 | 一次误触造成画作或对局中断 | 只在确实有画作 / 活跃对局时做简短确认；撤销维持一步完成 |
| P1 | 同一页面向所有角色展示整排 disabled 画具、禁用输入框。源码及上轮截图 | 页面有很多自己不能用的控件，却弱化了真正任务 | 画师看画具，猜词者看输入，出题者看待裁定列表；观看者看清楚状态 |
| P2 | 结果只在回合栏和消息中出现，分数变化藏在默认收起的玩家列表。源码及截图 | 猜中缺乏反馈，很难看清谁得分、下一步做什么 | 画作保留，紧凑结果卡显示答案 / 获胜者 / 加分 / 下一轮入口 |
| P2 | 投稿弹窗初始焦点在“关闭”；填名称后 Escape 关闭再开，内容清空。线上实测 | 开始输入多一步，容易丢草稿 | 桌面合理聚焦首字段；同一次登录内保留投稿草稿，显式清空 |
| P2 | 普通 radio / checkbox / details、文本图标、按钮密度混杂。线上大厅与源码 | 看起来像拼接的表单，选中与可操作状态不够统一 | 一套组件尺寸 / 选中 / focus / loading 规范；图标同源 |
| P2 | 房间码复制成功不自动恢复，失败静默。源码 | 用户无法区分后续动作是否成功 | 短暂“已复制”并恢复；失败保留可选文本与说明 |
| 待验证 | 手机输入法弹出、中文组合输入回车、触笔与横屏。未在真实设备验证 | 无横向溢出并不等于输入和绘画顺手 | 将这些列为验收场景，不能用桌面缩窄截图代替 |

原生 dialog 已经提供模态基础，当前代码也有 Escape 和焦点返回；升级目标是完整产品行为和视觉一致性，不应把已具备的能力误报为缺失。

定位文件：`client/src/App.jsx`（请求和全局反馈）、`GameRoom.jsx`（角色 / 猜词 / 结算）、`CanvasBoard.jsx`（工具）、`PackDialogs.jsx` / `Dialog.jsx`（弹窗）、`styles.css`（全局控件与移动尺寸）。

## 3. 哪些复用，哪些专门设计

| 部分 | 实现来源 | 具体用途 |
| --- | --- | --- |
| Button / Input / Textarea / Badge | 按需采用 shadcn 源码 | 统一尺寸、错误、loading、icon-only、选中和禁用样式 |
| Dialog / AlertDialog / Popover / Tooltip | shadcn 的 Radix 版本 | 投稿、确认、笔宽 / 调色浮层、桌面操作解释；保留默认键盘与焦点机制 |
| RadioGroup / Checkbox / ToggleGroup / Slider | 按实际需要采用 | 模式选择、词包多选、笔 / 橡皮切换与线宽；模式使用 radio 语义，不能误用导航 Tabs |
| 短通知 | Sonner 的 shadcn 接入 | 复制、投稿成功；错误和断线不全部塞进自动消失的通知 |
| 图标 | Lucide React，静态按需导入 | 画笔、橡皮、撤销、分享、退出；手机不能只依赖悬停提示解释图标 |
| DrawingToolbar / GuessComposer / GuessFeed / RoundStatus / RoundResult / PlayerStrip | 本项目定制 | 这是游戏独有的体验，组件库无法替代 |
| CanvasBoard 绘制与同步部分 | 保留并与工具界面拆开 | 继续使用现有增量绘画、epoch、恢复规则，不更换画布引擎 |

初期只引入正在使用的基础件。手机弹层先用同一 Dialog 实现响应式布局，确有手势需求再评估专用 Drawer；不为视觉效果加入一整套拖拽或动画框架。简单头像使用昵称首字与稳定配色，不增加头像服务。

可直接感受的参考：[按钮状态](https://ui.shadcn.com/docs/components/radix/button)、[弹窗与滚动内容](https://ui.shadcn.com/docs/components/radix/dialog)、[滑杆](https://ui.shadcn.com/docs/components/radix/slider)、[切换组](https://ui.shadcn.com/docs/components/radix/toggle-group)。参考其控件完成度，在本项目中使用暖色主题和中文排版。

## 4. 视觉规范与关键交互

### 视觉规范

- 暖纸背景、浅纸表面、墨色正文、橙色主要动作；另设明确的成功 / 警告 / 错误色。强调色不承担所有状态。
- 正文优先可读，辅助文字减少目前大量 10–11px；移动输入保持 16px。标题保留适量衬线风格，控件用清楚的系统无衬线字体。
- 统一 4px 间距基准、少量圆角与两档阴影。桌面常规控件高度 40px，紧凑操作 36px；触摸操作目标至少 44px，视觉图标可以更小。
- 每个交互组件明确 normal / hover / pressed / focus-visible / selected / pending / disabled / error。禁用状态旁说明原因，避免整屏灰掉。
- 动效主要用短暂透明度和小幅位移，约 120–180ms；结果转场可略长。不让倒计时、列表和图标持续跳动；尊重 reduced-motion。

以上尺寸是本项目的设计目标，并非宣称 WCAG 对所有目标都要求 44px。相关规范的最小尺寸及例外见 [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。

### 作画

- 桌面工具条按“笔 / 橡皮、颜色、线宽、撤销 / 更多”分组，给出笔宽圆点预览。
- 手机固定一行主要操作；点颜色 / 线宽打开易点按面板。清空放在低频操作中，打开确认后才执行，不靠长按隐藏功能。
- 色块有名称和非颜色选中标记；桌面补 B / E / Ctrl或Cmd+Z 快捷键，只在画布上下文生效，不截获输入框编辑。
- 撤销 / 清空等待快照时保留当前画面，工具附近显示同步状态，继续遵守本轮已修复的 epoch 防护。

### 猜词与裁定

- 发送时仅当前提交按钮显示 pending，输入仍可编辑，焦点保持。第一版保持单条在途请求，允许先输入下一条，不引入复杂消息队列。
- 成功只清除与已发送内容相同的草稿，不能误删等待期间新输入的文本。失败保留原提交内容，并给出明确重试入口；未知结果不自动重复发送。
- 中文输入法选词的 Enter 不发送；正式 Enter 才提交。移动键盘弹出后输入仍可见，画面保持可观察；对软键盘的验证必须用真机补充。
- 查看历史时不强制滚到底部；有新消息时出现“新消息”入口。系统事件、自己答案、其他人答案、裁定状态有清楚的轻量区分。
- 裁定者有待裁定数量和相邻的正确 / 错误按钮，pending 针对答案 ID；连续裁错不引发整个页面锁定。

### 等待、结果、分享与投稿

- 等待人数不足时，把“邀请朋友 / 复制房间码”作为明确下一步，显示缺几人；人数足够后突出开始。
- 猜中 / 超时 / 房主结束各有结果说明，答案、得分和下一轮集中呈现。结果不遮住整张画，也不要求全体玩家关闭模态才能继续。
- 当前先做好复制房间码。如果增加邀请链接，需额外实现 URL 房间参数、登录后加入、无效 / 满房 / 过期处理，列为可选小功能，不能假定已有。
- 投稿显示有效词数、重复 / 超长词提示和示例；错误靠近字段，成功后才清草稿。管理员密钥仍只保留弹窗内存，不能跟随普通表单草稿保存。

## 5. 技术边界和迁移风险

1. **CSS 衔接是首要风险。** 当前有全局 button / input / label / dialog 等规则；Tailwind Preflight 和 CSS layer 会影响现有页面。先在第一批限定范围，整理旧规则为 legacy / 组件类，统一层级；不能复制文档中的“替换整个样式文件”步骤覆盖本项目。每迁移一个组件就删除对应旧规则，避免永久两套按钮样式。[Tailwind Preflight](https://tailwindcss.com/docs/preflight)。
2. 继续使用现有 React / Vite / JSX、原生表单状态和 WebSocket hook。公共 UI 放 `components/ui/`，游戏组合件放现有 components 目录；先形成真实复用，再提取公共 API。
3. 按动作拆分 pending，不引入全局状态库。HTTP / WS 版本合并和服务器计分仍是权威，反馈动画不提前宣布猜中。
4. 画布内部采样、离屏缓冲和同步状态保留；工具状态变更不重建整个绘画订阅。角色精简 UI 时保留画布 DOM，避免空闪或误清本地笔画。
5. 按需引入、静态图标导入；投稿 / 管理弹窗可单独加载。当前主 JS 构建约 80.47 kB gzip，第一批记录增量；建议首屏 JS 先以不超过 120 kB gzip 为项目预算目标，超出先分析构成。这是目标，不是已测量的组件库体积承诺。
6. 官网示例不是业务校验方案；接入后仍测试键盘、焦点、慢网络、真实触摸和高频操作。不为小项目一次引入完整表单框架、Storybook、手势框架或路由重构。

## 6. 分批实施顺序

各批在 `codex/` 本地分支上，聚焦提交、测试、审查后合并。先形成可操作样板，再扩展全站。

| 批次 | 交付 | 为什么按这个顺序 | 完成标准 |
| --- | --- | --- | --- |
| A. 组件规范与一段完整样板 | 暖纸主题；Button / Field / Dialog / Slider；一个可操作的画具 + 猜词区样板，含慢请求和错误状态 | 最快看见品质提升，验证 shadcn 与现有 CSS、包体、中文的匹配 | 同一组件全部状态一致；键盘可用；360/390 手机与 1280 桌面截图；实际点击验证。未通过不扩展迁移 |
| B. 对局核心体验 | DrawingToolbar、角色界面、局部 pending、连续输入、裁定、新消息提示、危险操作确认 | 游戏时间最长、收益最高；不要先花一批只美化登录页 | 连续操作和 1.5 秒响应延迟下仍顺手；保持 epoch / roundId 规则；猜词失败不丢输入 |
| C. 回合反馈与朋友在场感 | 等待引导、角色提示、倒计时、结果卡、常驻精简玩家条 / 得分 | 让开局、进行、结束有明确节奏 | 看一眼知道自己的任务、谁得分、谁开下一轮；画作一直可见 |
| D. 大厅与词包 | 模式选择、词包多选面板、房间卡、投稿草稿 / 字段校验、管理员列表 | 复用前面验证后的基础组件，避免重复造样式 | 创建 / 加入 / 投稿 / 审核整条流程统一；长文本、多词包、空列表处理完整 |
| E. 真机与最终打磨 | 软键盘、触摸、焦点、动效、对比度、性能、两种模式多人验证 | 用真实流程验收“成熟” | 下方矩阵通过；再发布 VPS，保留上一版回滚 |

样板是开发用的状态预览，可切换画师 / 猜词者 / 断线 / 提交失败，不连接真实比赛。产品页面不会显示这些开发控制。第一批无需建大型组件展厅。

不按“给所有页面换按钮 → 给所有页面换输入 → 最后再看看游戏”推进；每批交付一段真正能顺畅使用的流程。

## 7. 验收标准

### 视觉与操作

- 1280×720、1440×900、360×800、390×844，另补横屏；无横向溢出、孤立换行操作或浮层遮住提交入口。
- 桌面首屏同时看见画布与答案输入。手机键盘收起时主要操作可发现；键盘打开时输入可见并可观察画面，不用不断上下滚动找按钮。
- 所有主要触摸按钮有足够点击区域；焦点清楚，Tab / Shift+Tab / Escape / 方向键行为符合控件语义，退出弹层回到触发处。
- 弹窗长内容只在规定区域滚动；打开 / 关闭不让页面突然横移，关闭草稿不会静默丢失。
- 成功通知不推动画布；断线信息持续可见，重连不制造重复提示；错误文案说明下一步。
- 关键文字 / 图标检查对比度，选中不只靠颜色；支持系统减少动效设置。

### 状态与正确性

- 画师、猜词者、出题者、房主；等待、出题、绘画、猜中、超时、离人结束、断线、重连均有预览和实际验证。
- 在模拟 1.5 秒响应下，发送不锁整个界面；新输入不被旧请求清掉；失败保留内容，重复点击不产生重复请求。
- 裁定依然绑定具体 guessId；过期 roundId 不作用于下一轮；撤销等待时不发旧 epoch 新笔画。
- 回归测试针对连续输入、IME、焦点、草稿、异步失败等行为。基础样式修改主要用视觉检查，不堆积只验证 className 的测试。
- 完整 npm test / build 及依赖审计；最终两种模式多人浏览器测试。若变更实时发送路径，重跑十客户端测试；仅样式变化不反复压测生产。
- 浏览器缩窄和 jsdom 不能证明真实 iOS / Android 软键盘体验。真机未测试时明确记录，不写成“手机验收全部通过”。
